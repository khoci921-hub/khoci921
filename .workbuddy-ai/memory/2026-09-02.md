# 2026-09-02

## Bug: siswa klik "SIMPAN DB" di AI CV (ai_form.html) → tidak muncul apa-apa

Laporan: "pencet simpan ga ada tulisan sama sekali" (1 siswa).

### Root cause (paling utama)
`#toast-container` hanya ada di `index.html` & `admin.html`. Halaman standalone
(ai_form, apply-full, master-full, share, siswa-baru) tidak memilikinya, dan
`showToast()` di `js/init/util.ts` melakukan `return` diam-diam saat wadah tidak
ada → **semua** toast (sukses/gagal/info) hilang tanpa jejak. Jadi siswa tidak
pernah tahu apakah simpan berhasil atau gagal, dan kalau guard
`identitas.nama_lengkap` kosong terpenuhi, tombol terasa "mati" total.

### Perbaikan yang dilakukan
1. `js/init/util.ts` — `showToast()` membuat wadahnya sendiri
   (`ensureToastContainer()`) kalau belum ada di DOM.
2. `partials/scripts-shared.html` — wadah toast disuntik ke semua halaman
   standalone saat build (`build:html` mengganti region SCRIPTS_SHARED).
3. `js/pages/ai_form.ts` — guard nama kosong pakai toast `error` (bukan `info`),
   field `#f_nama` ditandai merah + difokuskan, fallback baca nama dari DOM,
   `console.warn/error` di semua jalur gagal.
4. `netlify/functions/_lib/ai/cv.ts` — `writeAiSubmission()`: tulis
   `ai_form_submissions` diulang sekali tanpa kolom opsional (`submitted_by`,
   `ai_updated_at`) kalau PostgREST menolak (HTTP 400 kolom tak dikenal); pesan
   error asli Supabase kini dikembalikan ke frontend.
5. `migrations/20260902_add_ai_form_submission_cols.sql` — migration + query
   diagnostik untuk kolom `submitted_by` & `ai_updated_at`.
6. `DEBUG-TODO.md` — item debug baru di bawah F5.

### PENYEBAB KEDUA — TERKONFIRMASI lewat information_schema (user jalankan)
Tabel `ai_form_submissions` produksi **TIDAK punya kolom `submitted_by`**
(sementara `ai_updated_at` sudah ada, timestamptz). Kode mengirim kolom itu di
body INSERT/PATCH → PostgREST menolak SELURUH write dengan HTTP 400 **PGRST204**
→ **simpan gagal total untuk semua kandidat**, bukan cuma 1 siswa.
Pola ini identik dengan `MASTER_COLUMN_MISSING` di `actions-master.ts`.

Perbaikan lanjutan:
- `migrations/20260902_add_ai_form_submission_cols.sql` — tinggal
  `ALTER TABLE ai_form_submissions ADD COLUMN IF NOT EXISTS submitted_by TEXT;`
  + backfill `'kandidat'`.
- `cv.ts` direvisi: `aiSubColEnabled` mengingat kolom yang ditolak supaya
  request berikutnya langsung valid (tidak ada 1 request gagal per simpan).

### Catatan penting
- `ai_data_json` di `ai_form_submissions` bertipe **jsonb**; kode mengirim
  `JSON.stringify(...)` → tersimpan sebagai jsonb string. Itu memang konvensi
  yang sama dengan `master_database_candidate` (dibaca dengan `JSON.parse`),
  jadi TIDAK diubah.
- Pola bug berulang di proyek ini: kode menulis kolom yang belum ada di Supabase
  → PGRST204 → seluruh simpan gagal. Sebelum menambah kolom baru di body
  PATCH/POST, pastikan ada migration-nya.
- Perubahan baru aktif setelah `bun install && bun run build` + deploy
  (`/js/pages/ai_form.js` & bundel adalah artefak build).
- Verifikasi syntax: `bunx -p typescript@5.9.3 tsc --noEmit --noResolve` pada
  file yang diubah → 0 error syntax. tsconfig: `strict: false`.

## Audit performa/keamanan backend (review kode, bukan perbaikan)

Hasil: `CODE_REVIEW_PERF_AUDIT.md` di root workspace (7 blocker, 13 suggestion, 7 nit).

### Temuan paling penting (sudah diverifikasi dari source, bukan dari DEBUG-TODO.md)
1. **`netlify-wrapper.ts:9-14` `clientIp()`** ambil `x-forwarded-for.split(',')[0]` =
   nilai kiri = **bisa dipalsukan klien** → SEMUA rate limit (login admin
   5/mnt, AI 10/mnt, Fonnte, lockout) bisa di-bypass cukup ganti header.
   Harusnya pakai `x-nf-client-connection-ip` atau entri PALING KANAN.
2. **`actions-auth.ts:352-390` `registerFcmToken()`** — tanpa sessionToken,
   `ident = null` dan semua cek `if (ident && ...)` dilewati → **write DB tanpa
   auth**; attacker bisa daftarkan FCM token sendiri ke nomor WA korban
   (hijack notifikasi).
3. **`ai/chat.ts:155-198` VIP lock** — 3 bypass: (a) kirim tanpa
   `currentData.identitas.hp` → blok gate dilewati total; (b) identitas dibaca
   dari payload klien, bukan dari token; (c) `!lookupError` = **fail-open**.
   Plus regex `isVipCatatan` (`chat.ts:125`) `[A-Z0-9]+` match semua tag
   kurung siku → hampir semua catatan lolos jadi VIP.
4. **`session.ts`** — token TIDAK punya `exp`, tak bisa dicabut; secret
   fallback hardcode `'asj-portal-local-secret'` ada di repo publik.
5. **`actions-mail.ts:23-47` + `db/forms.ts:144`** — `rowIndex` di-resolve
   pakai `order=timestamp.desc` TANPA tiebreaker → saat timestamp kembar
   (import massal / 1 kandidat lamar banyak job), approve/reject/delete
   **mengenai baris orang lain**. Fix: kirim `id` (sudah ada di `mapForm`),
   atau tambah `,id.desc` di SEMUA query list + index.
6. **`rate-limit.ts:22-39`** — `prune()` cuma jalan saat insert key BARU dan
   cuma kalau `size >= 20000`; kalau sweep tak menemukan yang expired,
   Map tetap tumbuh → memory leak + sweep O(n) tiap insert (CPU DoS).
7. **`pageSize` tidak di-clamp** (`actions-candidate.ts:110`,
   `actions-public.ts:199`) → `findCandidatesByIds` bikin `in.(...)` raksasa →
   414 → **fallback full-scan yang tidak di-cache**; cacheKey memuat
   `pageSize` mentah + `MAX_ENTRIES=50` → cache thrashing, semua user
   kena full scan. `handleGetMonthlyReport` sudah kirim `pageSize: 5000`.

### Pola berulang yang perlu diwaspadai
- `cacheClear()` dipanggil SEBELUM validasi & SEBELUM mutasi sukses
  (`actions-mail.ts:26`, `actions-candidate.ts:16`, `actions-auth.ts:196`) →
  request invalid/tidak sukses tetap mengosongkan cache global.
- Order by kolom non-unik tanpa tiebreaker (`timestamp.desc`) dipakai untuk
  resolve posisi → sumber bug salah-baris (sama dgn `urutkan` string compare
  di `actions-public.ts:204`).
- Error PostgREST (`db/client.ts:54`, 200 char body) diteruskan mentah ke
  klien → bocor nama tabel/kolom.
- Kode sudah benar: guard `requireAdmin` konsisten di semua handler mail
  (`actions-mail.ts:185,191,197,204,234`), `kind==='refresh'` ditolak,
  `timingSafeEqual` dipakai. Jangan klaim "banyak handler tanpa guard".
